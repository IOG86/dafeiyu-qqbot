## 链接打不开？按这个顺序查

```
1. 隧道在不在跑？   → 任务管理器里有没有 ssh 进程
2. 手动开一次隧道   → powershell -ExecutionPolicy Bypass -File "D:\dafeiyu\deploy\tunnel.ps1"
3. 服务器活没活？   → 上面那条 ssh 命令能不能连上
4. 容器起没起？     → 连上后 docker ps，看 astrbot / snowluma 是否 Up
5. 控制台没起？     → cd console && py -3 app.py
```

> 这是本项目里反复用到的一条网络知识：**端口绑 127.0.0.1 + SSH 本地转发（`-L`）**，
> 等价于"把远端端口安全地映射到本机"，比直接对公网开放面板安全得多。

## 2.2 SSH 与远程运维（网络工程的核心技能）

**我们做的**
- 密钥登录：Windows 上 `.pem` 必须**收紧 ACL**（否则 `UNPROTECTED PRIVATE KEY FILE`）
- 端口转发：`ssh -N -L 127.0.0.1:6185:127.0.0.1:6185 root@IP`
- 长连接保活：`ServerAliveInterval=20 ServerAliveCountMax=3`
- 排障时区分：**TCP 能连 ≠ SSH 能登录**

**知识点**
- 非对称加密 + 挑战应答（公钥存 `authorized_keys`，私钥不出本机）
- `known_hosts` 与主机指纹（为什么重置系统后 fingerprint 变了）
- 端口转发三种：`-L` 本地转发、`-R` 远程转发、`-D` 动态 SOCKS
- SSH 协议分层：TCP → 版本交换（banner）→ KEX → 认证 → 会话
- **banner 交换**是判断"网络通不通、服务活没活"的关键分界点

**练习**
1. 把服务器 6185 转发到本机 16185，用浏览器访问
2. 用 `-R` 把本机 22 反转到服务器，从服务器 SSH 回你的电脑（理解 NAT 穿透）
3. `ssh -v` 逐行读握手日志，标注每个阶段

## 2.3 计算机网络（这个项目信息量最大的一块）

**我们遇到的真实问题**
1. Docker Hub 被墙 → 只能用镜像加速
2. 服务器公网**回程丢数据包**：请求能到、响应回不来
3. IP 安全组、NAT、与"换 IP/换地域"的关系
4. 用代理、换路径做对照实验定位问题

**知识点串讲**

| 层次 | 概念 | 本项目对应 |
|---|---|---|
| 传输层 | TCP 三次握手 / RST / 重传 | 能连上但卡 banner；`nstat` 看重传 |
| 传输层 | MTU / MSS / PMTUD | `ping -f -l` 测路径 MTU |
| 网络层 | NAT / 公网 IP / EIP | 停机再启动可能换 IP |
| 应用层 | HTTP / WebSocket / SSH 协议识别 | noVNC 走 WS，OneBot 走 WS |
| 安全 | 安全组（云防火墙）/ iptables / nftables | `iptables -S`、`nft list ruleset` |
| 中间设备 | DPI、限速、QoS、流量清洗 | 长连接被掐、包被丢 |
| 名字解析 | DNS / resolv.conf / systemd-resolved | 曾怀疑 sshd 反向 DNS 卡住 |

**排障工具箱（务必都会）**
```bash
ping / traceroute          # 连通性与路径
ss -tlnp / ss -tn          # 谁在监听、有哪些连接
curl -v / curl -sN         # HTTP 细节、SSE 流
tcpdump -i any -nn -A      # 抓包看内容（终极武器）
ip -s link                 # 网卡错包/丢包计数
nstat -az | grep Retrans   # TCP 重传统计
cat /proc/pressure/io      # 内核级 I/O 阻塞指标
```

**这次最值钱的一课：分层定位法**
> 现象：SSH 一直 "Connection timed out during banner exchange"。
> ① 先测 TCP 能不能连上 → 能（说明不是 firewall/路由完全不通）
> ② 再测服务器有没有发 banner → 用裸 socket 读到 `SSH-2.0-OpenSSH...`
> ③ 再测客户端发出版本号后有没有回应 → 没有
> ④ 服务器侧日志：`kex_exchange_identification: read: Connection reset`
> ⑤ 在服务器上自己连自己 → **握手完成，到认证阶段失败**（说明 sshd 本身健康）
> ⇒ 结论：**服务端正常，是链路上应用层数据被丢/被掐**。于是换路径（代理）验证、最终靠重置系统盘恢复。
> **没有一步是猜的，每一步都有一个可观测证据。**

**练习**
1. 在服务器抓一次自己的 SSH 登录：`tcpdump -i any -nn port 22 -c 20`
2. 用 `curl -v http://127.0.0.1:6185/` 读懂请求/响应头
3. 用 Python 裸 socket 连 22 端口，只读 banner（体会"应用层数据"和"TCP 连接"是两回事）

## 2.4 Docker 与容器化

**我们做的**
- 用 compose 跑两个容器，端口全部 `127.0.0.1` 绑定
- 内存上限 `mem_limit/memswap_limit`、`shm_size`、`cap_add: SYS_PTRACE`、`seccomp=unconfined`
- 数据卷（bind mount）持久化，`docker cp` 取文件，`docker stats` 看资源

**知识点**
- 镜像 = 只读层叠加；容器 = 镜像 + 可写层
- 容器不是虚拟机：共享内核，靠 namespace 隔离、cgroup 限资源
- **端口映射**本质是 docker-proxy + iptables/nftables DNAT
- compose 的服务名就是容器网络里的 DNS 名（所以 `ws://astrbot:6199` 能解析）
- `restart: unless-stopped` 与开机自启、`systemctl enable docker` 的配合
- `shm_size`：/dev/shm 默认 64MB，Chromium/QQ 会崩，必须调大

## 2.8 性能与稳定性（1.6G 机器的血泪史）

**这台机器的三次生死**
1. QQ 登录同步 → 磁盘写爆 → load 17、I/O 压力 99% → SSH 死
2. 装 xdotool 的 apt 写入 → 又是一次写放大
3. 内存吃紧 → swap/zram 反复换页 → I/O 升高

**知识点**
| 概念 | 说明 | 本项目数值 |
|---|---|---|
| load average | 1/5/15 分钟平均"可运行+不可中断"任务数，要除以核数看 | 2 核，load>4 就很糟 |
| available vs free | `free` 要看你 `available`，不是 `free` | 目标保留 >150MB |
| page cache | 缓存占的内存可回收，不是"用掉了" | buff/cache 600MB 正常 |
| **PSI** | `/proc/pressure/io` 的 `full avg10` 是"所有任务都因 I/O 卡住"的比例，比 load 精确 | 正常 <5%，>50% 要熔断 |
| dirty pages | 脏页攒太多会一次性回写堵死磁盘 | `dirty_ratio=10` 而非默认 20 |
| zram | 内存里做压缩交换，省磁盘但吃 RAM | 512M 上限，别开太大 |
| cgroup | Docker 的 `mem_limit` 靠它，超了 OOM kill 容器而不是拖死整机 | astrbot 450M / snowluma 900M |
| IO 调度器 | `mq-deadline` 对低 IOPS 云盘更稳 | `/sys/block/vda/queue/scheduler` |

**看门狗设计（一个实用的工程模式）**
```
每 30s 采样 PSI/I-O + 内存 → 连续 3 次超阈值 → 停掉最"重"的容器 → 写日志
目的：牺牲单个业务，保住整机 SSH 可运维性（"可观测性 > 可用性 > 性能"）
```

**练习**：用 `stress-ng --io 2` 压 I/O，同时观察 `load`、`/proc/pressure/io`、`iostat` 的变化曲线。

## 2.11 软件工程与运维实践

**我们做的**
- 插件化扩展（4 个插件，其中 2 个自研）
- 配置优先级排坑：**同名键在顶层/嵌套/运行时三处都有，要递归改**
- 钩子优先级：AstrBot 按 priority **从高到低**执行，负数越小组越晚；我们的注入被 `-260000` 的钩子覆盖过，改成 `-300000` 才生效
- 热重载（插件 reload）代替重启
- 幂等脚本：`if 已存在则跳过`、备份 `.bak.时间戳`
- 密钥管理：`.env` 权限 600、密钥文件 ACL 收紧

**知识点**
- 配置的"单一事实来源"问题（同一份配置多处存储 → 必然踩坑）
- 插件生命周期：初始化 → 注册钩子 → 热重载 → 销毁
- 幂等（idempotent）是运维脚本的第一原则
- 变更留痕：备份 + 时间戳 + 可回滚

**练习**：写一个"安装 nginx 并保证重复执行不报错"的脚本（幂等）。

## 2.12 排障方法论（比任何工具都重要）

**通用流程**
```
1. 明确现象（可观测的描述，不是"坏了"）
2. 分层定位（物理→链路→网络→传输→应用→业务）
3. 找边界：什么通、什么不通；换目标/换路径/换客户端做对照
4. 收集两侧证据（客户端抓包 + 服务端日志）
5. 提假设 → 设计能证伪它的实验 → 一次只改一个变量
6. 修复 → 回归验证 → 写复盘
```

**本项目 10 个真实案例速览**

| # | 现象 | 根因 | 用到的知识 |
|---|---|---|---|
| 1 | 镜像拉不下来 | Docker Hub 被墙 | registry 镜像、代理 |
| 2 | 机器 load 17、SSH 卡死 | QQ 登录写盘 + apt 写放大 | PSI、脏页回写、IOPS |
| 3 | SSH 卡 banner、能连不能登 | 公网回程丢包 | TCP/应用层分层、对照实验 |
| 4 | 云助手命令超时 | 前台命令超执行时限 | 后台执行 + 日志轮询 |
| 5 | `docker compose` 报连不上 daemon | 应急时 stop 了 docker.socket | systemd 服务依赖 |
| 6 | QQ 掉线要重扫 | 同账号被其它电脑顶下线 | QQ 会话机制 |
| 7 | 私聊回复发送失败 | outputpro 给私聊加了 @ | QQ 消息元素限制 |
| 8 | 注入的提示词不生效 | 被更高/更晚的钩子覆盖 | 插件优先级 |
| 9 | 它管用户叫 astrbot | 模型复述上下文账号名 | prompt 约束 + 反例 |
| 10 | 改的配置重启后还原 | 插件按 schema 重建配置 | 配置优先级 / 嵌套结构 |

# 结语

这次项目真正的收获不是"机器人能聊天了"，而是：

1. **你敢在真实环境里动一台公网服务器**（这是课程实验给不了的）
2. **你经历了一次完整的"故障—定位—修复—加固"闭环**
3. **你学会了用证据说话**：每一步判断都有命令输出支撑，而不是"我感觉"

这三件事，比会背 OSI 七层更值钱。把这台机器当成你的实验室，坏了大不了重置系统盘——**现在你有备份脚本、有文档、有复盘记录，这就是工程师的样子。**
